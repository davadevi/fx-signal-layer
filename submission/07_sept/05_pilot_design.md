# FX Signal Layer — Pilot Design

**Alfa-Bank Hackathon · Сентябрь 2026**

---

## 1. Цель пилота

Проверить гипотезу: **push-уведомление о выгодном курсе увеличивает вероятность перевода в течение h=10 рабочих дней со средним курсом не хуже курса в день сигнала.**

Пилот не проверяет модель — он проверяет продуктовую гипотезу: реагируют ли клиенты на сигнал, и улучшается ли их фактический курс транзакции.

---

## 2. Коридоры для пилота

| Коридор | Обоснование | Статус |
|---------|-------------|--------|
| **RUB/KGS** (кыргызский сом) | IS lift 2.1–2.2, OOT 1.8–2.2, CI > 1.15 на h=5,10 | ✓ Рекомендован |
| **RUB/TJS** (таджикский сомони) | IS lift 2.35–2.52, OOT 1.76–2.13, CI > 1.65 на h=5,10 | ✓ Рекомендован |
| **RUB/AMD** (армянский драм) | IS lift 2.81, OOT 2.16, CI > 1.30 на h=10; N=4 (мала выборка) | ⚠ Кандидат, осторожно |
| RUB/UZS | CI < 1.0 на всех горизонтах | ✗ Не включать |
| RUB/KZT | Нет OOT сигналов | ✗ Не включать |

---

## 3. Дизайн A/B теста

### Рандомизация

- Единица рандомизации: **клиент** (не транзакция).
- Клиенты, совершавшие переводы по KGS/TJS/AMD за последние 6 месяцев, рандомно делятся на группы.
- Split: 50% группа A / 50% группа B на уровне corridor × client_id.

### Группа A (treatment)

Получает push-уведомление в момент срабатывания сигнала (score < 0.20, confirm_days=2, cooldown 3d).

Push-текст (пример для KGS):
```
"Рубль укрепился к сому значительнее, чем в 85% дней за 3 месяца.
Текущий курс: 1.4320 руб."
```

### Группа B (control)

Не получает push-уведомление. Переводы совершаются в обычном режиме.

## 4. Первичные метрики

| Метрика | Определение | Ожидаемый эффект |
|---------|-------------|-----------------|
| **Курс транзакции (A vs B)** | Средний курс фактических переводов в группе A vs B в окне [t, t+10d] после сигнала | A лучше B на 1–3% |
| **Конверсия после сигнала** | Доля клиентов группы A, совершивших перевод в течение h=10 дней | > конверсии B в тот же период |

Первичный успех: **курс транзакции A ≥ курса транзакции B** статистически значимо (p < 0.05, one-sided).

---

## 5. Вторичные метрики

| Метрика | Определение |
|---------|-------------|
| Open rate | Доля клиентов, открывших push-уведомление |
| CTR → приложение | Клик из push → открытие раздела переводов |
| Conversion rate | Открыл push → совершил перевод в [t, t+10d] |
| Частота переводов | Среднее число переводов/мес в группе A vs B |
| Opt-out rate | Доля клиентов, отписавшихся от уведомлений |

---

## 6. Стоп-критерии

Досрочная остановка пилота при любом из условий:

| Условие | Порог | Действие |
|---------|-------|----------|
| Lift < 1.0 на накопленных 100 событиях | OOT lift < 1.0 по факту | Остановить, пересмотреть порог |
| Opt-out rate > 15% | >15% клиентов отписались | Остановить, изменить частоту/текст |
| Жалобы на push-текст | Любая жалоба на «предсказание» или «давление» | Немедленная остановка, compliance review |
| Технический сбой stateful cooldown | Дублирующие сигналы в течение cooldown | Остановить, починить pipeline |

## 7. Длительность пилота

Оценка на основе частоты сигналов:

| Коридор | Freq/нед | Событий за 3 мес | Событий за 6 мес |
|---------|----------|-----------------|-----------------|
| KGS | 0.057 | ~0.7 | ~1.5 |
| TJS | 0.065 | ~0.8 | ~1.7 |
| Итого (2 коридора) | ~0.12 | ~1.5 | ~3.2 |

**Проблема:** при текущей частоте 0.057–0.065 сигн./нед — один сигнал на коридор примерно раз в 2–3 недели. За 6 месяцев при клиентской базе N ≥ 500/коридор можно накопить ~3–4 события уровня corridor × signal-date.

**Минимальная база:** для 50 событий на коридор при 50% конверсии клиентской базы нужно ~17 лет при текущей частоте.

**Вывод по длительности:** пилот не ограничен по времени — ограничен числом сигналов. Рекомендуется:
- Минимальный горизонт: **12 месяцев** или **20 signal-events** (whichever first).
- Анализировать промежуточно после каждых 5 событий.
- Параллельно исследовать увеличение частоты (weak-tier, дополнительные коридоры).

## 8. Допущения и риски

| Допущение / риск | Описание | Митигация |
|-----------------|----------|-----------|
| Репрезентативность OOT | OOT-период (2025-07-01+) мал (N=4–8 событий); пилотная частота может отличаться | Накапливать статистику в реальном пилоте; не экстраполировать OOT-метрики |
| AMD малая выборка | N=4 в OOT; lift 2.81 может быть шумом | Запустить AMD позже, после верификации KGS/TJS |
| Cooldown взаимодействие с A/B | Если cooldown работает по corridor-level, клиент B "блокирует" сигнал для клиента A | Cooldown должен быть независим по A/B группам |
| ARPU vs курс | Клиент A может реагировать позже h=10; метрика урезает эффект | Добавить анализ с расширенным окном h=20 |
| Корреляция коридоров | KGS/TJS/AMD коррелируют 0.83–0.97 с USD/RUB; сигналы могут срабатывать одновременно | Cooldown cross-corridor не нужен; A/B независим по коридорам |
| Compliance | Push в период регуляторных изменений может быть неуместным | Мониторить новостной фон; стоп-критерий по жалобам |

## 9. Техническая готовность pipeline к пилоту

| Компонент | Статус | Примечание |
|-----------|--------|------------|
| Генерация сигналов | ✓ Готов | `src/pipeline/signals.py`, `generate_signals()` |
| Stateful cooldown | ✓ Готов | `data/signal_history.json`, 30-дневная ретенция |
| Compliance validator | ✓ Готов | `src/texts/templates.py`, все шаблоны проверены |
| Backtest ↔ runtime sync | ✓ Готов | Единая логика фильтрации |
| Push delivery | ✗ Не реализован | Требует интеграции с push-системой банка |
| A/B split логика | ✗ Не реализован | Требует client_id → group mapping |
| Метрики отслеживания | ✗ Не реализован | Требует event logging на уровне транзакций |

Для запуска пилота необходимо реализовать: push delivery, A/B split, event logging.
